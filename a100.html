1 Introduction

The goal of this work is to see how few SMs we can use to saturate the HBM of an A100, and explain hardware fundamentals along the way.

2 Background

This problem is interesting to me for several reasons.

First, its relevance (to me) comes from the fact that we see an emergence of warp-specialization in performant GPU kernels, i.e., where we have a group of producer warps that solely focus on transporting data to the GPU (shared memory, tensor memory), and a group of consumer warps that focus on using transported data for computation (and also do the write-back, since that is cheap).
Thus, if we can keep our producer warps as light as possible (only one SM per GPC, or most ideally, one light-weight warp per SM), this frees up many valuable resources (registers) for our consumer warp groups.

Second, I love optimizing things in constrained environments. It’s like a puzzle that tests your understanding of the problem and the hardware (and compiler and operating system), and it requires you to be conscious about every single instruction that executes. (This is why I love programming in RISC ISAs1 and C.)

3 Strategies

This first set of kernels has the objective of saturating the HBM with as little SMs as possible

3.1 Kernel k0 — straightforward

For a simple kernel that doesn’t utilize any special PTX instructions, the following was clear to me:

  • We want to do the most simple thing, a vector “memcpy”, i.e., B[i] = A[i] for i in [0..n-1]
  • Most obviously, we want our intra-warp memory accesses to be coalesced (and generally coalesced inter-warp2)
    • We can achieve this via each thread accessing a contiguous 16-byte (float4) element based on threadIdx.x. Then, a warp accesses \(16 \times 32 = 512\) contiguous bytes
  • We want to maximally utilize the registers of our SMs
    • Each four-register group (because each register is 32-bits and we are using float4 which grabs four contiguous fp32) can be used to load data. Thus, outside of setting aside some registers for our pointers and address calculation, we want to maximize the number of four-register groups that have pending data in-flight from global memory
  • We want one, persistent block per SM
    • Having multiple blocks per-SM is pointless, and makes our SM-counting very difficult, so let’s use one block per SM. Plus, one persistent block is much more performant, since a new block has to awkwardly fill the empty pipeline with loads before it can start issuing stores. One persistent block can continuously load future data while issuing stores (yay pipelining!)
  • It’s easier to let the compiler optimize things if everything is a constant expression (known at compile-time), and for simplicity (and performance), everything is a power-of-two
    • This means compile-time vector length, which unrolls the copy loop, which creates compile-time address offsets (SASS supports constant address offsets up to )
  • We want each thread to have the maximum number of registers (255)
    • Maximal register usage per-thread will allow for the least warp-switching, and more-importantly, means the less redundancy of storing arguments (since each thread needs the pointers in its own registers)
    • Modern SMs have 64K registers per SM, so with a limit of 255 registers per thread, this gives \(\frac{64 \times 1024}{256} = 256\) threads per SM

With all of this in place, we can get to the following simple kernel:

constexpr int SMALL_NUM_STEPS = NUM_THREAD_BLOCKS_NEEDED / SMALL_SMs_USED;

__global__ void
small_SMs(const float4* __restrict__ dA, float4* __restrict__ dB) {
    constexpr int step = BLOCKS_PER_SM * SMALL_SMs_USED * THREADS_PER_BLOCK;
    const int idx = blockIdx.x * THREADS_PER_BLOCK + threadIdx.x;

    #pragma unroll
    for (int i = 0; i < SMALL_NUM_STEPS; ++i) {
        dB[i * step + idx] = dA[i * step + idx];
    }
}

So nice and simple. (You can see that I love compiler hints; we’ll see the emergence of more hints later.)

3.1.1 Idea

What about enqueuing multiple loads before then trying to store? E.g., instead of load A[0], store A[0], load A[1], store A[1], we can do load A[0], load A[1], store A[0], store A[1], as this separates dependencies?
Thankfully, the compiler will handle this for us when generating the SASS! (This is called instruction scheduling.)

3.1.2 Expectation

Let’s run some back-of-the-envelope math (what inspired this). Resources suggest that:

  • An HBM request takes ~500 core cycles
  • An A100 has 80 memory channels, each channel serving many banks
  • To fully saturate a channel, you should have ~21 128B requests per channel (because it’s heavily pipelined)

Note:  I decided to pause my deep-dive on the HBM2 internals (via the open-standard) to get through the rest of this, but this is safely an over-approximation of what the A100 is capable of. This section just gives a very general idea of expectation, but it intentionally lacks specifics (until I learn more).

Thus, we can determine that we need \(21 \times 128 \times 80\) bytes being simultaneously served over 500 clock cycles.

So with each thread containing 255 registers, say it uses 248 for memory operations, then each thread can contribute \(248 \times 4\) bytes. With this being vectorized into 4, we issue 62 instructions to achieve this, and with pipelining, it seems reasonable to expect this to execute within 500 cycles.

This then implies that we only need \(\frac{21 \times 128 \times 80}{248 \times 4} < \frac{21 \times 128 \times 80}{21 \times 4 \times 11} < 32 \times 8 = 256\) threads, which can fit into a single SM!

Except this is only going to saturate the HBM for one memory cycle. Let’s break it down.
From a single SM’s perspective, it will take one memory cycle to prepare the DRAM and then one memory cycle of full utilization to get the data it requested. It will then send data to store and then follow this up with another load.
But the store will require one memory cycle to get ready, so we can see that a single SM saturates the HBM every-other memory cycle. This implies that we would require two SMs to fully saturate the HBM (besides the first memory cycle, which will always be empty).

This makes two key (and false) assumptions about memory:

(1) The actual transfer of data between the SM and DRAM is instantaneous, but it requires one memory cycle for it to actually be read/written from/into the DRAM.
(2) There is no limit to how many memory requests an SM can issue and how much data it can await/outstanding.

I think that (1) is not too inaccurate in terms of data transportation speed, but I know that it is especially limited by the fact that each bus can only tranport data unidirectionally, i.e., it can only be transporting data from DRAM to SM, or SM to DRAM.
So, if you want to issue a store after reading, you’ll have to wait for the read to finish using the bus before you can send your store on the bus.

There are some more ways of limit-testing this that I hope to expand upon further in the future. For instance, to counter the load vs store of (1), you can have a read-heavy kernel rather than a memory-transfer kernel. E.g., summing a vector.

Testing (2) would be possible via using half the registers and double the SMs, for instance.

3.1.3 Result

Alas, when we test, we observe that it takes 34 SMs to reach HBM saturation on our A100 (btw, this is an A100 SXM4 with 1310 GB/s, and it has 108 SMs total).

Now, of course there are those two limitations I stated above, and there is plenty of room for optimizations (skipping caching, cp.async, prefetching), but this is worse than I expected.

3.2.2 Explanation

There’s two issues that we see in the SASS:
(1) It is only storing a few elements at a time before issuing more loads. This yields poor performance because the memory buses can only transfer reads or writes, not both, as I briefly mentioned in the limitations at the bottom of the Expectation section
(2) This issue isn’t visible in the SASS snippets that I provided, but we are also running into an issue that our memory instructions can no longer fit the address offset into the instructions’ immediate value.
You can see it for yourself here. See how we go from loads and stores to these IMAD and IADD instructions.

I’m going to ignore (1) for now because it is very painful to try and edit the SASS which is emitted, so let’s continue and hope that it doesn’t appear when we apply other optimizations.
When you do these kinds of optimizations one-by-one, it’s a great way to learn the effectiveness of various optimizations, but some weird “issues” like this don’t appear after applying other optimizations. Which is nice, of course, but really makes you kick yourself for all of that wasted investigating4…

We can address (2) in the next kernel.

3.2.3 Quick failed optimization

I was trying to think of ways to reduce register pressure on the PTX side-of-things, and I realized that we could allocate one large blob of global memory, and then assign dA to the first half, and dB to the second half.

From the PTX perspective, this looks nice! We saved ourself two registers (since GMEM addresses are 64 bits)!

However, this was before I had realized that issue (2) was happening.
With (2), it’s immediately5 clear why this failed: we still have to use a separate register for the address of dB since \(dB > dA + \text{MAX\_IMMEDIATE\_VALUE}\).

I want to also add that this failed extremely hard because there is no possible method that I was able to find of getting ptxas to accept that &dB[0] >= &dA[NUMEL]. Even with __builtin_assume() compiler hints. It deemed my creation of dB from dA as possibly overlapping, and thus, all of the reads and writes were serialized.

This meant that it looked like

load r0, a[0], 
store b[0], r0 
load r0, a[1], 
store b[1], r0

Which is horrible!!

But even with a perfect ptxas, as I mentioned above, this optimization achieves nothing6.

3.3 Kernel k1_0 — ptr increment

So, to counteract the fact that our pointer-offsets are becoming extremely large, we can implement an age-old compiler trick: we just increment the pointer rather than having a loop variable which determines the offset.
This is historically useful for saving a register (and instruction), but it is quite nice here to avoid the mess of address calculation.

And why can’t nvcc just handle this itself? Well, I think that a large part is due to the fact that we’re just fully unrolling the loop before we perform optimization passes, so it’s probably harder for nvcc to spot this? Ultimately, we don’t know.
(NVIDIA plz open source ,–__–)

So our kernel looks like:

__global__ void 
__launch_bounds__(THREADS_PER_BLOCK, BLOCKS_PER_SM)
small_SMs(const float4* __restrict__ dA, float4* __restrict__ dB) {
    const int step = BLOCKS_PER_SM * SMALL_SMs_USED * THREADS_PER_BLOCK;
    const int idx = blockIdx.x * THREADS_PER_BLOCK + threadIdx.x;

    #pragma unroll
    for (int i = 0; i < SMALL_NUM_STEPS; ++i) {
        dB[idx] = dA[idx];
        dA += step;
        dB += step;
    }
}

3.4 Kernel k1_1 — grouped_inner_loop

So what we want is for the pointers to be incremented right before the offset becomes larger than the largest possible immediate operand.

We can achieve this with the following kernel:

constexpr int GROUP_SIZE = 512;

__global__ void 
__launch_bounds__(THREADS_PER_BLOCK, BLOCKS_PER_SM)
small_SMs(const float4* __restrict__ dA, float4* __restrict__ dB) {
    const int step = BLOCKS_PER_SM * SMALL_SMs_USED * THREADS_PER_BLOCK;
    const int idx = blockIdx.x * THREADS_PER_BLOCK + threadIdx.x;

    for (int i = 0; i < SMALL_NUM_STEPS; i += GROUP_SIZE) {
        #pragma unroll
        for (int j = 0; j < GROUP_SIZE; ++j) {
            dB[j * step + idx] = dA[j * step + idx];
        }
        dA += step * GROUP_SIZE;
        dB += step * GROUP_SIZE;
    }
}

I picked GROUP_SIZE based on the fact that: by observation, SASS memory operations can support immediates of -0x800000 to 0x7fc000,
so then we want to increment our pointer address by 0x1000000 = \(2^{23}\), so then group size should be:
\(\frac{2^{23}}{\texttt{step} \cdot 16} = \frac{2^{23}}{4 \cdot 256 \cdot 16} = 2^{23 - (2+8+4)} = 2^{23 - 14} = 2^9 = 512\)

Note:  Even if we didn’t increment the pointers, and instead used the offset (i + j) * step + idx, the compiler will still increment the pointers for us so that we don’t have to use a constant. It generates slightly different code, you can see here.

But this kernel has the following problem:
The SASS now looks like 32 loads, then 32 stores, and then it loops back. But as I mentioned above, while it’s nice to burst our loads/stores because of the data bus, we would ideally like to always have outstanding loads.
The reason is that stores are “instant” in terms of they instantly create an available register7.

3.4.1 Limitations

We would like loads/stores that looks like our Listing 1.
We should just have a prologue that loads everything, a main loop that issues a burst of stores followed by a burst of loads, and then an epilogue of stores.

But you can’t really control how ptxas does everything. And while it’d be nice to fully trust ptxas’s decisions, they’re not always optimal

3.5 A pitstop

Well, let’s carry-on then, ignoring (1) still.
There are two straightforward optimizations that we can apply from here:

  1. Ensuring that we’re not caching our loads/stores (since we won’t reuse them)
  2. Using shared memory or prefetching to decrease the latency of other data (since they don’t occupy instructions)

3.6 Kernel k2 — cache_policy

This is the beginning of our inline-assembly journey for these kernels! But that means that the kernel will become less readable…

We need to first see what cache-behavior specifications load and store instructions support. See here, but the T;LDR is that we want to pick cg because this means that it skips the L1, and only goes to L2 (passing through L2 is required).

We define the following two inline functions:

__device__ __forceinline__
float4 load(const float4* p) {
    float4 v;
    asm volatile("ld.global.cg.nc.v4.f32 {%0, %1, %2, %3}, [%4];"
        : "=f"(v.x), "=f"(v.y), "=f"(v.z), "=f"(v.w)
        : "l"(p));
    return v;
}

__device__ __forceinline__
void store(float4* p, float4 v) {
    asm volatile("st.global.cg.v4.f32 [%0], {%1, %2, %3, %4};"
        :: "l"(p), "f"(v.x), "f"(v.y), "f"(v.z), "f"(v.w)
        : "memory");
}

And then change our kernel to look like:

__global__ void 
__launch_bounds__(THREADS_PER_BLOCK, BLOCKS_PER_SM)
small_SMs(const float4* __restrict__ dA, float4* __restrict__ dB) {
    const int step = BLOCKS_PER_SM * SMALL_SMs_USED * THREADS_PER_BLOCK;
    const int idx = blockIdx.x * THREADS_PER_BLOCK + threadIdx.x;

    for (int i = 0; i < SMALL_NUM_STEPS; i += GROUP_SIZE) {
        #pragma unroll
        for (int j = 0; j < GROUP_SIZE; ++j) {
            store(&dB[(i + j) * step + idx], load(&dA[(i + j) * step + idx]));
        }
        dA += GROUP_SIZE * step;
        dB += GROUP_SIZE * step;
    }

}

If you inspected the code, you may notice the .nc in our ld.global instruction.
The ld.global.nc instructions utilize the non-coherent cache. It’s not the most well-documented thing, but ptxas emits it on our loads because we specified const __restrict__, so we’ll follow suit.

3.7 Kernel k3 — shared_memory

We’re now ready to get to the hopefully most obvious optimization that awaits us on Ampere, utilizing shared memory via cp.async instructions! They’re outlined here, but the TL;DR is that the instruction can directly tranport data from global memory to shared memory without intermediately using a register!

This means that we can issue as many loads from global memory to shared memory, with the amount of available shared memory being the only limiting factor.

We just have to synchronize before reading to ensure that it finished transporting the data.

3.7.1 Optimizing in-flight requests

Let’s first see how much shared memory each thread can have.
So the max per-block shared memory that we can allocate is 163KB on an A100.
Splitting this up amongst 256 threads, we get \(163 \cdot 4\) bytes per thread. Then, a single float4 occupies 16B, so each thread can load \(\frac{163 \cdot 4}{16} > 40\) elements (unfortunately, 3KB will just sit unutilized, but it would get messy to use it).

These cp.async don’t occupy/hold any of our registers, so this means that we still have all of our registers for loading/storing! It literally only costs us one register, the shared memory pointer.
So we literally get 60% more data for free (we hope)!

We can try to interleave shared memory loads with global loads:

load shared[0..39], a[0..39]
load four-reg[0..20], a[40..60]
load four-reg[21..60], shared[0..39]
store b[0..39], four-reg[21..60]
load shared[0..39], a[60+0, 60+39]
store b[40..60], four-reg[0..20]
load four-reg[0..20], a[100..120]
load four-reg[21..60], shared[0..39]
...

Upon reading the PTX 11.0 documentation (main CUDA Toolkit release for sm_80, which is what we need for A100), I discovered that the GPU supports prefetching (I wasn’t aware of this before).

4 Lessons

4.1 Look at the SASS!!!

This is probably the biggest lesson. Even just taking our first kernel, looking at its PTX, we may really doubt its performance. All of the loads and stores are streamlined. This may lead us on an adventure where we have a prologue, main loop, and then epilogue, and ensure that we access a constant-sized array with constand indices to ensure that it stays as registers…

But we don’t need to do this upon inspecting the SASS. We see that ptxas handles instruction scheduling (sometimes against our wishes, as we saw in Explanation for k0).

On the other hand, we won’t be able to detect that the constant doesn’t fit into the immediate operand for memory instructions by looking at the PTX either. This is the kind of subtle thing that is very easy to miss when working at the PTX-level only. (This is generally not very relevant because it’s quite rare to have huge constant offsets, but the point stands.)

5 Methodology

We can test how well the kernel performs with three means really:

  1. We don’t see a speedup by adding more SMs than our minimal amount (e.g., increasing number of SMs launched from 4 \(\to\) 16 gives no speedup)
  2. We can see how close we can get to 90% SOL for memory transfer
  3. We can compare against a standard memory transfer kernel that utilizes most of the SMs

All three are equivalent for our purposes, so let’s just use the third one since it is nicely portable.
